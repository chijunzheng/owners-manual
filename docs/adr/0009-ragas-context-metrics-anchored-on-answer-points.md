# RAGAS context metrics anchored on the golden answer points (reference-based, RAG-only)

Pins HOW the RAGAS context columns score a RAG arm's retrieved context — the open question `evals/src/owners_manual_evals/ragas_live.py` surfaced (*"which RAGAS metrics, which LLM/embedding wrapper"*, left provisional) and that the #18 scaffold deferred to an ADR (#46). Settles the **anchor** (what the metrics measure *against*), the evaluator seam, and the Vertex wiring before the live RAG-only context columns go on. Builds on [ADR 0005](./0005-provider-split-vertex-gemini-runtime-claude-offline-batch.md) (Gemini on Vertex for runtime/secondary-judge) and is the retrieval-side analog of [ADR 0008](./0008-judge-invocation-claude-cli-offline-batch.md) (the Claude answer judge).

## Forces

- The #18 scaffold committed to **two** context columns — `context_precision` + `context_recall` — gated to the RAG arms only (`naive-rag`, `agent`) and left blank for the stuffing arms, which have no retrieval to measure. `four_arm_dashboard.py` renders exactly these two as RAG-only markers; that shape is not reopened here.
- The golden set's textual ground truth is the per-item **answer points** — hand-verified, claim-level, and deliberately paraphrased (Crown copyright keeps statute text out of the repo). The `required_cites` are *addressing-only* citable paths, and the document trees are *structure-only* (Part → section → subsection → clause, no provision text): a cite resolves to an **address**, never to text.
- RAGAS context-**recall** has no reference-free variant. `LLMContextRecall` decomposes a reference *answer* into claims and checks each against the retrieved context; `NonLLMContextRecall` needs ground-truth reference-context *strings*. Both require ground truth. Only context-**precision** has a reference-free form (`LLMContextPrecisionWithoutReference`, anchored on the produced answer).
- The dashboard already carries deterministic, cite-based retrieval signal — **Retrieval hit rate** (the fraction of an item's required cites whose paths reached the candidate set, by exact hierarchical match) — and the offline judge (ADR 0008) already grades the *produced answer* claim-by-claim against the same answer points. A new metric must measure something neither of those does, or it is noise.
- Provider: ADR 0005 fixes Gemini-on-Vertex as the runtime model and the same-family secondary judge on the GCP credit. The Claude credit (ADR 0008) is `claude -p`-shaped, not a LangChain chat object RAGAS can wrap, and Claude-on-Vertex is credit-excluded — so RAGAS's evaluator LLM is Gemini-on-Vertex by elimination, not preference.

## Decision

1. **Anchor — reference-based on the golden answer points.** Synthesize one **reference answer** from an item's `answer_points` and score the retrieved context against it with `LLMContextPrecisionWithReference` (each retrieved chunk's usefulness toward the reference) and `LLMContextRecall` (each reference claim's attribution to the retrieved context). This is the only anchor that fills *both* committed columns from the hand-verified ground truth. *(Here "reference" means the ground-truth **answer**, not a Pin-cite — the glossary's `_Avoid_: reference` note is about citations.)*
2. **Scope — the two retrieval columns only; the produced answer stays out of them.** These columns measure RETRIEVAL, not generation. The produced answer is already evaluated by the judge (ADR 0008) + point score; keeping it out of the context metrics is exactly what lets a failure be attributed to retrieval vs generation — the same split **Retrieval hit rate** owns, here on the semantic axis. No faithfulness / answer-correctness column ships in #46 (a different metric family with different gating — see alternatives).
3. **Complement, never duplicate, Retrieval hit rate.** RAGAS `context_recall` is the **semantic** measure — *is the verified answer's meaning supported by the retrieved text?* **Retrieval hit rate** is the **structural** measure — *did the cited provisions' paths reach the candidate set?* They can diverge (right path retrieved but the needed content sits in an un-retrieved sibling; or sufficient content present under a different path than the required one) and are reported side by side, never blended.
4. **Seam — `(question, contexts, reference)`.** The `ContextEvaluator` carries exactly what the two metrics consume; the produced `answer` and the retrieved path keys are dropped from it. The `answer_points → reference` synthesis is a pure, unit-tested helper (`reference_from_answer_points`) in `ragas_metrics.py`, newline-joining the point texts — the points are already discrete claims, so the join hands `LLMContextRecall` a pre-segmented reference. The live binding stays a thin forwarder.
5. **Evaluator LLM — Gemini on Vertex via RAGAS's LangChain wrapper.** `build_ragas_context_evaluator` wraps a `ChatVertexAI` (the ADR 0005 Vertex provider) in RAGAS's `LangchainLLMWrapper`; the model is read from a dedicated `RAGAS_VERTEX_MODEL` env var (fail loud if unset, mirroring ADR 0008's `JUDGE_CLAUDE_MODEL`). It MAY be set to the product `DEFAULT_MODEL` but is pinned independently. Both chosen metrics are **LLM-only** — no embedding wrapper, so RAGAS adds **no embedding dependency**.
6. **`ragas` is a lazy-imported, declared dependency.** Declared in `evals/pyproject.toml` (its own optional/eval group), imported lazily inside `ragas_live.py` so it stays out of the offline unit suite's dependency surface (matching the Langfuse / Agent-SDK convention). The metrics module and its RAG-arms-only gate stay pure and unit-tested against `scripted_context_evaluator`; the live binding is `pragma: no cover`, live-by-design.
7. **Per-item, with a sync boundary.** One item per RAGAS evaluation (`single_turn_ascore`), preserving per-item independence as the judge does (ADR 0008). The async RAGAS call is bridged to the synchronous `ContextEvaluator` inside the live binding, so the four-arm loop and the seam stay synchronous.

## Consequences

- `ragas_live.py` conforms: the `NotImplementedError` body builds a `SingleTurnSample(user_input=question, retrieved_contexts=contexts, reference=reference)`, scores `LLMContextPrecisionWithReference` + `LLMContextRecall` over the Vertex-wrapped Gemini, and returns `ContextMetrics`. Still behind the seam; the offline suite is untouched.
- `ragas_metrics.py`: the `ContextEvaluator` seam changes from `(question, contexts, answer, required_cites)` to `(question, contexts, reference)`; `scripted_context_evaluator` and `test_ragas_metrics.py` move to the new contract (the RAG-only gate and the metric shape stay pinned against the fake). A new pure helper `reference_from_answer_points` lands with its own test.
- `compare_four_arms.py`: the call site builds `reference=reference_from_answer_points(item.answer_points)` and drops the `answer=` / `required_cites=` arguments.
- The dashboard's two RAG-only columns are now semantically defined and sit beside **Retrieval hit rate** as its structural counterpart; the legend / CONTEXT.md state that RAGAS recall is semantic and Retrieval hit rate is structural, so a divergence between them is information, not a bug.
- The "verified once against live Gemini-on-Vertex on a small slice" check is an OPERATOR step (needs the GCP credit + a produced retrieval to score), like the Atlas re-ingest and the judge verify (ADR 0008) — not a CI job. RAGAS columns stay opt-in: a `None` evaluator leaves them off and the table still renders; they are never a per-PR gate.
- Embeddings stay out of RAGAS; no new embedding cost. RAGAS calls bill to the GCP/Vertex credit (ADR 0005).

## Considered alternatives

- **Reference-free (`LLMContextPrecisionWithoutReference`, anchored on the produced answer).** Needs no ground truth and is cheap, but RAGAS has **no reference-free context-recall**, so it cannot fill the committed second column; it ignores the hand-verified ground truth the whole golden set exists to provide; and it would have a Gemini judge grade context-usefulness against a Gemini-*produced* answer — same-family self-reference, the exact bias ADR 0005 engineered the Gemini-product / Claude-judge split to avoid — while confounding retrieval quality with whatever the generator happened to do. Rejected.
- **Reference-based on `required_cites` resolved to provision text** (`NonLLMContextRecall` over reference-contexts, or an LLM reference built from cited text). The intuitive *"did retrieval surface the cited provisions"* reading — but the document trees are structure-only and statute text is Crown-copyright-excluded from the repo, so **there is no text to resolve a cite to**; sourcing it would mean the raw corpus (uncommitted) or the live index (circular — that is the retrieval under test). And the structural version of this question is **already** answered deterministically by **Retrieval hit rate**, exactly and without an LLM. Rejected: not buildable as framed, and redundant where it is.
- **Add faithfulness / answer-correctness in #46 too.** Directly "evaluates the answer" and is valuable, but it is a different metric *family* (generation, not retrieval): it applies to all four arms, not RAG-only, so it changes the dashboard shape and gating, and answer-correctness / answer-relevancy largely duplicate the judge + point score. Out of scope for #46; **faithfulness** (the low-overlap one — answer grounding / hallucination against the retrieved context) is the candidate if a generation column is ever added. Deferred.
- **Carry the produced answer / retrieved paths through the seam anyway ("future-proofing").** Keeps the seam stable across a hypothetical faithfulness addition, but it carries inputs the chosen metrics never consume and invites exactly the reference-free confusion this ADR exists to settle; a faithfulness metric would live in its own module with its own seam regardless. Rejected in favor of an honest, minimal seam.
